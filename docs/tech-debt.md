# Tech debt ledger

Known, deliberate, and written down rather than discovered later. A cross-module promise that is
not enforced on the other side belongs here, not in a comment.

Everything here is a day or two of work. The gaps that are bigger than that — and the designed
answers to them — are in [known-gaps.md](known-gaps.md): what the gates are structurally unable to
catch, what would close each one, and what it would cost.

| ID | Item | Why it is debt | Cost of fixing |
| --- | --- | --- | --- |
| TD-0001 | Balance is a projection with no reconciliation job | `SUM(ledger_entry)` and `ledger_balance` can only diverge through a bug, but nothing would tell us | 1 day: a nightly job + a metric |
| TD-0002 | Outbox relay polls; no `LISTEN/NOTIFY` | Adds up to one poll interval of latency to event propagation | 0.5 day |
| TD-0003 | Retry schedule is per-redemption, not per-operator | One operator being down burns attempts for every redemption instead of opening a circuit | 2 days: a per-tenant circuit breaker in `integration` |
| TD-0004 | Entitlement expiry runs as a cron sweep | A spin on an expired-but-unswept entitlement is still accepted inside the sweep window | 0.5 day: check the TTL in the claim predicate as well |
| TD-0005 | No rate limiting on the player API | A player can hammer `/v1/spins`; correctness holds (entitlements run out) but the cost is ours | 1 day |
| TD-0006 | Admin API authorises by tenant key, with no roles | Any operator key can change that operator's wheel odds; there is no "read-only analyst" | 2 days once roles exist |
| TD-0008 | `postgres` is pinned to 3.x because 4.x is ESM-only and this is a CommonJS project | NestJS, `tsc`, swc and vitest are all on the well-trodden CJS path here; going ESM means suffixing every relative import with `.js` | 1 day, as one change: `"type": "module"`, `moduleResolution: nodenext`, extensions everywhere, then unpin |
| TD-0009 | Operator signing secrets are encrypted with a key derived from `PLAYER_TOKEN_SECRET` by HKDF | One secret with two HKDF-separated purposes is sound, but a real deployment wants independent, rotatable, KMS-managed keys — and rotation here means re-encrypting every row | 2 days: a key-id column on the ciphertext, a KMS provider in `platform/crypto`, and a re-encrypt job |
| TD-0010 | Append-only is enforced by a TRIGGER; the withheld `DELETE`/`TRUNCATE` privilege is only the second half | `mio_app` is granted `UPDATE` on every table, `ledger.entry`, `gamification.spin`, `gamification.wheel_version` and `infra.audit_log` included, so `infra.refuse_mutation` is the only thing refusing an UPDATE. Privilege alone is not the control, and a trigger can be disabled by the table's owner | 0.5 day: revoke `UPDATE` on the append-only tables specifically, so privilege and trigger agree |
| TD-0011 | A lease re-claim may ask the operator to grant the same reward a SECOND time | The lease recovers a worker that died between the operator call and recording the outcome, and recovery means asking again. Nothing on our side can prevent the duplicate: the call carries `Idempotency-Key: redemption:<id>`, honouring it is the operator's decision, and neither simulated operator here keeps a key store. Measured with a real `SIGKILL`: two grants, one charge. What is implemented instead is that the ambiguity is RECORDED — the claim increments `grant_requests` before the call, so an `issued` redemption with `grant_requests > 1` is on the reconciliation list, reported by the status API and logged on completion. The player is never charged twice; the operator may be out one reward | 2 days, and most of it is not code: a reconciliation job that reads `grant_requests > 1` against each operator's own grant history, which needs an endpoint or a report we do not have from either of them. A cheaper half-step is a daily metric on the count, so the exposure is known even before it can be settled |
| TD-0012 | `red-check` measures added test FILES, so test cases added into an existing spec file are never proved red at the merge-base | The gate's whole claim is "a test you cannot see fail is not a test", and a new `it(...)` in a file that already exists bypasses it entirely — which is how every test of the first fix round entered the repository (round-two review R2-B3). The run now names the modified spec files instead of being silent, and `test-guard` requires a `test-fix:` declaration for each, but a declaration is a sentence and not a measurement | 2–3 days: extract the `it(...)`/`test(...)` bodies a branch ADDS inside a modified file, synthesise a spec from them beside the original, and run that at the merge-base. The hard parts are not the parsing but the sharing — an added case usually leans on `beforeEach` and helpers from the rest of the file, so the synthesised file has to carry the whole module scope and only the new cases, and a wrong answer here fails correct work closed |
| TD-0013 | No statement, transaction, lock or pool-acquire timeout anywhere | `database.ts` passes `max`, `onnotice` and `transform` and nothing else, and postgres.js's acquire queue is unbounded and untimed — so a saturated pool makes callers wait instead of failing, and no query is ever cut off. Round two reached the ceiling with twelve concurrent issuances against a 600 ms operator: ten connections busy, two callers queued, nothing wrong. For money code, "no statement will ever be cut off" should be a decision rather than an omission (round two S11) | 0.5 day: `statement_timeout`, `idle_in_transaction_session_timeout`, `lock_timeout`, `connect_timeout` and an acquire timeout, each configurable, plus one test per limit. The care is in the numbers — the sweep's cross-tenant query and the integration suite are the two things a careless value fails |
| TD-0014 | `docker compose up -d --scale worker=2` fails on a port clash | The worker service publishes `3002:3002`, so the one service the architecture says to run several of cannot be scaled by the compose file that runs it; round two had to start its extra workers with bare `docker run`. The mapping is there so the host can read `:3002/health`, which the first-run documentation uses (round two S10) | 15 minutes, and it is a trade: drop the host mapping and `--scale` works but `curl :3002/health` does not, or publish an ephemeral host port and the docs stop naming 3002 |
| TD-0015 | `markDueForIssuance`'s `isNull(nextAttemptAt)` guard has no test | Deleting the predicate leaves the whole suite green (round two's mutant M5). The guard is correct — a redelivered `rewards.redemption.requested` would otherwise reset `next_attempt_at` to now and throw away an accumulated backoff — but it is the only mechanism in the lease work with nothing behind it, and a clause with no test is what a later refactor deletes as redundant (round two S8) | 1 hour: one integration test that redelivers the event on a redemption whose retry is already scheduled forward, and asserts the schedule did not move |
| TD-0016 | "`execute` has exactly one caller" is prose, and the module exports the means to break it | The invariant that keeps the operator's HTTP call outside a transaction holds in this tree — the only production caller is `IssuanceWorker` — but `IssueRewardUseCase` is a public export of `rewards`, so a future consumer can call it from inside its own transaction and silently restore the defect the first review raised. The use case already injects the unit of work, and `UnitOfWork.inTransaction()` already exists, so the invariant can be enforced where it is stated (round two S12) | 1 hour: refuse to run when a transaction is already open, and a test that proves the refusal. This is the house rule about cross-module promises applied to the module's own facade |
| TD-0017 | A failing outbox tick logs at `error` level every poll interval, forever | Against an unmigrated or unreachable database that is four lines a second with no backoff and no deduplication, which is how a log that nobody reads is made. The relay's per-event failures already back off; the tick itself does not (round two S6) | 1 hour: back off the tick on consecutive identical failures and log the first at `error` and the repeats at `debug`, with a test that counts the lines |
