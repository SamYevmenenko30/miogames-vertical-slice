# SPEC: MIO-004 — ingestion: authenticate, validate, deduplicate, emit one event

Card: board/1-in-spec/MIO-004-deposit-ingestion.md · Revision 1 · Author: agent (Claude), 2026-11-20

## Context

Steps 1 and 2 of Part B, and the first Part C cases: duplicate deposit events, and invalid or
unauthorized ones. This module decides nothing about rewards — it decides whether an event is
real, whether we have seen it before, and records it.

Governed by [ADR-0003](../decisions/ADR-0003-idempotency-outbox-and-retries.md).

## Decisions taken here

- **Accept-then-process.** The request persists an envelope and an outbox row, and answers. The
  rules engine runs in the worker. Nothing an operator waits on depends on our gamification.
- **Deduplication is a unique constraint**, `(tenant_id, operator_event_id)`, with
  `ON CONFLICT DO NOTHING`. Not a read followed by an insert, which races with itself.
- **The envelope is stored for every authenticated request**, before interpretation and whatever
  the outcome — accepted, duplicate, invalid or unsupported. An operator dispute is settled by
  what they sent, not by what we made of it.
- **Signature over `${timestamp}.${rawBody}`**, headers `X-MIO-Key-Id`, `X-MIO-Timestamp`,
  `X-MIO-Signature`, with a tolerance window. Without the timestamp inside the MAC a captured
  request replays forever.

## Behaviour spec

- **S1 — a correctly signed deposit is accepted.** `POST /v1/ingest/casino-a/events` with a valid
  signature answers `202` with an `eventId`, stores one envelope with outcome `accepted`, and
  writes exactly one `casino.deposit.observed` row to the outbox, carrying the canonical event.
- **S2 — a replay returns the first answer and causes no second effect.** Posting the same
  `event_id` again answers `200` with the **same** `eventId` and `status: "duplicate"`, adds no
  outbox row, and stores a second envelope recorded as `duplicate`.
- **S3 — concurrent duplicates still produce one event.** Five simultaneous deliveries of the
  same operator event id yield exactly one outbox row and one distinct `eventId`.
- **S4 — a bad signature, an unknown key and a stale timestamp are all 401, and alike.** Each
  answers `401` problem+json with the same `type`; nothing in the body or status distinguishes
  "wrong secret" from "no such key". No envelope is stored for an unauthenticated request,
  because we cannot attribute it to a tenant.
- **S5 — a malformed deposit is 422 and says which field.** A deposit whose `user_id` is empty
  answers `422` with the dialect's reason in `detail`, stores an envelope with outcome `invalid`,
  and writes no outbox row.
- **S6 — an event we do not act on is acknowledged, not refused.** A `withdrawal.completed`
  answers `202` with `status: "ignored"`, stores an envelope with outcome `unsupported`, and
  writes no outbox row. An operator must not have to distinguish our feature set from an error.
- **S7 — the player is not provisioned by ingestion.** Ingestion stores the external player id as
  the operator sent it; no `identity.player` row appears until the worker handles the event.
- **S8 — tenant isolation.** An event signed with tenant B's key lands under tenant B, even if its
  payload names a player that exists in tenant A; tenant A sees no envelope and no outbox row.
- **S9 — `GET` writes nothing.** There is no `GET` on this module that creates or mutates a row.

## Open questions

- **Q1 — what if the operator event id is reused for a genuinely different deposit?** →
  **Answered** (agent default, 2026-11-20): we treat it as a duplicate and do nothing. The
  envelope of the second delivery is stored, so the difference is visible in audit, and the
  operator is told `duplicate`. Guessing that "this one is different" would mean rewarding a
  deposit twice on an operator's bug, which is the more expensive mistake.
- **Q2 — should an unauthenticated request be recorded at all?** → **Answered** (agent default,
  2026-11-20): not in `ingestion.envelope`, which is tenant-owned and would need a tenant we do
  not have. It is logged with the key id presented and the source address, which is where a
  brute-force pattern is visible anyway.
