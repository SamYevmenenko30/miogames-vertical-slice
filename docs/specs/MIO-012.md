# SPEC: MIO-012 — observability and auditability: request context, structured logs, readable audit

Card: board/1-in-spec/MIO-012-observability-and-audit.md · Revision 1 · Author: agent (Claude), 2026-11-20

## Context

In a money-shaped system, "what happened to this redemption" has to be answerable from stored
facts rather than reconstructed. Three things make that true: every log line carries the request's
identity, every configuration change and money movement is in an append-only log, and the process
can say whether it is healthy and against which schema.

## Decisions taken here

- **One trace id per request, returned to the caller.** `X-Trace-Id` on every response, including
  errors, so a support conversation starts with an identifier instead of a timestamp.
- **The audit log is read through the module that owns it** — an inbound adapter on the admin
  surface, scoped to the tenant by the same `scopedWhere` as everything else.
- **`/health` reports the applied schema version** and refuses to claim health if the database is
  unreachable. It does not run migrations.
- **Metrics are named, not faked.** There is no metrics backend here; `docs/observability.md`
  lists what we would emit and why, which is more useful than a dashboard of invented numbers.

## Behaviour spec

- **S1 — every response carries a trace id.** A successful request and a failing one both return
  `X-Trace-Id`, and the value in the header matches the `traceId` in a problem+json body.
- **S2 — the trace id is the same one the logs carry.** Within one request, log lines written by
  different layers share the request's trace id.
- **S3 — `/health` reports the applied schema version.** `GET /health` answers `200` with
  `{ ok: true, schemaVersion: "<latest migration file>" }`; with the database unreachable it
  answers `503` and does not claim `ok`.
- **S4 — the audit log is readable per tenant, newest first.** `GET /v1/admin/audit` with the
  operator's credentials returns that tenant's entries, newest first, with `action`, `actor`,
  `subjectType`, `subjectId` and `data`.
- **S5 — the audit log is not readable across tenants.** Tenant B's read does not contain tenant
  A's entries, even for the same `action`.
- **S6 — secrets never reach the log.** A log call carrying `secret`, `apiKey`, `signature` or an
  `authorization` field writes `[redacted]` in their place.

## Open questions

- **Q1 — should the trace id be accepted from the caller?** → **Answered** (agent default,
  2026-11-20): not yet. Accepting an inbound `X-Trace-Id` is how distributed tracing starts, and
  it also lets a caller collide two requests' logs on purpose. When we adopt W3C trace context it
  comes in as `traceparent`, validated, which is a different ticket.
- **Q2 — does the audit log need its own retention?** → **Answered** (agent default,
  2026-11-20): yes eventually, and it is a question for the operator's regulator rather than for
  us. Recorded in the 90-day plan under compliance, not invented here.

## Out of scope

- A metrics backend, dashboards, distributed tracing, log shipping. All named in
  [docs/observability.md](../observability.md) and the 90-day plan.
