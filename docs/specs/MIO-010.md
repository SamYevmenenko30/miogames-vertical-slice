# SPEC: MIO-010 — rewards: issuance through the operator adapter, with timeouts, retries, refunds and a status API

Card: board/1-in-spec/MIO-010-reward-issuance.md · Revision 1 · Author: agent (Claude), 2026-11-20

## Context

Steps 7 and 8 of Part B, and four Part C cases at once: external API timeouts, failed reward
issuance, retries and eventual recovery. This is where the system meets something it does not
control.

Governed by [ADR-0003](../decisions/ADR-0003-idempotency-outbox-and-retries.md).

## Decisions taken here

- **Failure is classified, never "unknown".** A timeout, a connection error and a 5xx are
  *retryable*; a 4xx, a malformed answer and an unregistered operator are *terminal*. Defaulting
  to retry on a terminal failure burns the attempt budget against a request that can never
  succeed.
- **A failed issuance refunds in full** (Sam, 2026-11-20), as a compensating credit keyed
  `redemption:<id>:refund`.
- **The idempotency key travels to the operator**, so a retry is recognisable on their side too.
  We cannot enforce that they honour it; we can make it possible.
- **Backoff is exponential with jitter, capped**, and lives on the redemption row — not in
  memory, so a restarted worker resumes the schedule.

## Behaviour spec

- **S1 — a successful issuance reaches `issued` with the operator's reference.** The worker
  consumes `rewards.redemption.requested`, calls the tenant's adapter, and the redemption becomes
  `issued` with `externalRef` set and `lastError` cleared.
- **S2 — both operator dialects work from the same intent.** Operator A receives a flat REST body
  (`user_id`, `reward_type`, `reward_value`) and returns `{reference}`; operator B receives a
  command envelope (`command: GRANT_REWARD`, `reward: {kind, units}`) and returns
  `{result:{commandRef}}`. Both end as `issued`, and the reference is stored verbatim.
- **S3 — a timeout is retryable and leaves the redemption claimable.** With the operator told
  never to answer, the attempt ends within the configured timeout, `attempts` becomes 1,
  `lastError` names a timeout, and the status returns to `pending_issuance` with
  `nextAttemptAt` in the future.
- **S4 — a 5xx is retryable; a 4xx is terminal.** A 500 schedules a retry. A 422 marks the
  redemption `failed` immediately, without consuming the remaining attempts.
- **S5 — an operator that fails twice and then recovers ends as `issued`.** Three drains against
  a mock configured to fail twice: `issued`, with `attempts` reflecting the two failures.
- **S6 — attempts are bounded, and exhaustion refunds.** After `ISSUANCE_MAX_ATTEMPTS` retryable
  failures the redemption is `failed` and the coins are credited back with idempotency key
  `redemption:<id>:refund`; the balance returns to what it was before the redemption.
- **S7 — the refund is idempotent.** Running the failure path twice credits once.
- **S8 — a terminal failure refunds too.** A 4xx leaves the player's coins where they were.
- **S9 — the status API exposes the lifecycle.** `GET /v1/redemptions/:id` reports `status`,
  `attempts`, `lastError` and `externalRef` as they change.
- **S10 — issuance is claimed exactly once.** Two workers draining the same redemption produce
  one operator call: the `pending_issuance → issuing` transition is a conditional UPDATE.

## Open questions

- **Q1 — what if the operator answers 200 but without a reference?** → **Answered** (agent
  default, 2026-11-20): terminal. A success we cannot record is not a success — we would have no
  way to answer "was this reward issued?" and no way to reconcile. The refund path makes it
  financially neutral and the error is visible in `lastError`.
- **Q2 — should a failed redemption be retryable by hand?** → **Answered** (agent default,
  2026-11-20): not in this slice. The coins are refunded, so the player can redeem again, which
  is a cleaner story than resurrecting a failed row. An operator-side "issue it anyway" is a
  support tool, not an invariant.

## Out of scope

- Per-operator circuit breaking and rate limits (TD-0003), an admin re-drive endpoint (Q2).
