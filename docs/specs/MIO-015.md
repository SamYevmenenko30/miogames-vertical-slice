# SPEC: MIO-015 — round-two review: the claim's write-back, the recorded grant, the pools, and three gates that did not bite

Card: board/3-in-progress/MIO-015-round-two-review-fixes.md · Revision 1 · Author: agent (Claude), 2026-11-20

## Context

[The round-two adversarial review](../review/adversarial-review-round-2.md) re-measured the
round-one fixes and attacked the code that closed them, which nobody had reviewed. It found four
blockers. Two are money defects the lease introduced (R2-B1, R2-B2), one is a hole in the gates
that predates both rounds (R2-B3), one is the residue of a partly-fixed gate (R2-B4). This card is
its "what I would insist on before this is submitted" list.

The review itself is evidence, not a plan: every finding carries an executed reproduction, and
every suggested remedy is a suggestion. One of them — putting `claimed_by` in the write-back
predicate — does not work until R2-B2's prerequisite, a genuinely unique instance id, is in place,
because `issuance-${process.pid}` collided across two containers during the review's own run.

Governed by [ADR-0003](../decisions/ADR-0003-idempotency-outbox-and-retries.md).

## Decisions taken here

- **A claim is identified per claim, not per process.** `claimed_by` carries
  `<instanceId>/<uuid>`: unique to one act of claiming, and still naming the worker that took it,
  which is what the column was for. A per-process id would be enough for two racing containers and
  not enough for one process that re-claims a redemption its own earlier attempt is still inside —
  and that attempt is exactly the one whose write-back must be refused.
- **A lost claim is news, not an error.** A worker that comes back to find its claim gone has
  learned that a peer finished the work. It logs, at `warn` with the claim it was holding, and
  returns. It does not retry, does not refund and does not publish.
- **The write-back and its consequences are one decision.** The refund and the
  `rewards.redemption.failed` event live in the same transaction as `markFailed` and are now
  conditional on it having matched a row. Tightening the `UPDATE` alone would still have paid the
  player.
- **Asking the operator is recorded before the operator is asked** (Sam, 2026-11-20 — see Q1). The
  claim is that record: it increments `grant_requests` and stamps `grant_requested_at`, and it
  commits before the call goes out. `attempts` keeps its existing meaning — attempts that failed —
  so a recovered redemption is no longer indistinguishable from a clean success without changing
  what any existing statement means.
- **A re-claim is reconcilable, not safe.** Three places said an operator's `Idempotency-Key`
  makes it safe. Neither simulated operator honours that key, and no real one can be made to, so
  the claim was false inside the system as shipped. It is now stated as what it is: a second grant
  may happen, and `grant_requests > 1` is how anyone finds out. TD-0011.
- **`red-check`'s crash-red declaration becomes per-file.** It was an aggregate, so one
  assertion-red file switched the rule off for every undeclared crash-red sibling.
- **`.only` and a skipped test belong in a gate.** A committed `.only` disables its siblings and a
  committed `.skip` satisfies `pnpm verify` while proving nothing: both are the theatre the
  pipeline exists to prevent, and neither was checked anywhere.

## Behaviour spec

- **S1 — a write-back requires the claim it was taken under.** `markIssued`, `scheduleRetry` and
  `markFailed` match only a row that is still `issuing` and still carries this worker's exact
  claim, and each reports whether it matched.
- **S2 — a stale lease holder's failure does not refund a reward that was issued.** Worker A
  stalls in the operator call past its lease; worker B re-claims and issues; A returns a terminal
  failure. The redemption stays `issued` with B's reference, the coins stay spent, no compensating
  credit is written, and no `rewards.redemption.failed` event is published.
- **S3 — a stale lease holder's retryable failure does not resurrect an issued redemption.** The
  same race with a retryable failure leaves the redemption `issued`, not back in
  `pending_issuance` where the sweep would issue it again.
- **S4 — a worker that finds its claim gone says so.** It logs at `warn`, naming the redemption
  and the claim it was holding, and returns without writing.
- **S5 — two claims of one redemption are two different claims.** A re-claim after the lease
  expires stores a `claimed_by` different from the one the first claim stored, even when both are
  taken by the same process, and both values name the instance that took them.
- **S6 — an instance id identifies a process, not its pid.** Two independently loaded
  configurations never share an `instanceId`, it names the host it runs on, and `INSTANCE_ID`
  overrides it so an orchestrator can name the pod. (That the relay and the issuance claim both
  *take* it from configuration is wiring, verified by reading — a test asserting it would be
  asserting the source text, which is the kind of test R2-B4 is about.)
- **S7 — asking the operator is recorded before the call.** The claim transaction increments
  `grantRequests` and sets `grantRequestedAt`, and it commits before the operator is called, so a
  process that dies during the call leaves the request recorded.
- **S8 — a redemption issued on its first call records exactly one grant request.** So
  `grantRequests > 1` means what it says.
- **S9 — a redemption recovered after a worker died *after* the grant records two.** It ends
  `issued`, and `grantRequests` is 2 — the operator was asked twice for one redemption, which is
  the ambiguity the lease buys and is now visible on the row instead of looking like a clean
  first-attempt success.
- **S10 — the status API reports the grant record.** `GET /v1/redemptions/:id` returns
  `grantRequests` and `grantRequestedAt`, so "exactly what we sent and when" is true of the lost
  attempt too.
- **S11 — an issuance completed after more than one grant request is logged for reconciliation.**
  At `warn`, naming the redemption, the count and the operator's reference.
- **S12 — shutting the application down closes both database pools.** After `app.close()` neither
  the application pool nor the owner pool accepts another query. (`db:seed` returned; a worker
  container stopped in under the ten-second grace period rather than being `SIGKILL`ed, which is
  the crash S9 above makes recoverable and S7 makes recordable.)
- **S13 — `test-guard` refuses a deleted spec file with no declaration.** `git rm` of a spec test
  is a modification of the strongest kind and needs `test-removed:`, `test-fix:` or
  `spec-conflict:`.
- **S14 — `test-guard` refuses a spec file renamed and edited in one commit.** Git reports it as
  `R<similarity>`, which matched neither of the gate's two filters. A rename with no edit at all is
  a move and passes with a note.
- **S15 — `test-guard` refuses `.only` and a skipped test in a committed spec file.** `.only`
  unconditionally; `it.skip` / `describe.skip` / `.todo` unless the commit declares
  `test-skipped: <path> — <why>`.
- **S16 — `red-check` requires every crash-red file to be declared.** An assertion-red sibling no
  longer excuses an undeclared crash-red file.
- **S17 — `red-check` names the spec files it cannot measure.** It measures added files only, so
  test cases added into an existing spec file are unmeasured; the run says so and names them
  instead of being silent about it.

## Open questions

- **Q1 — the lease recovers a wedged issuance by asking the operator to grant a second time. Accept
  it as a known limit, or record the request so a recovery can be reconciled?** → **Answered**
  (Sam, 2026-11-20): record it. The duplicate grant stays — it cannot be removed without an
  operator-side guarantee we do not have — but a redemption whose outcome is unknown must not be
  written down as a redemption whose outcome was a clean success. The claim records the request
  before the call, the count is on the row and in the status API, and a completed issuance with more
  than one request is logged. The residual risk is TD-0011, not a solved case.
- **Q2 — should `attempts` count operator requests instead of failures, so one column tells the
  whole story?** → **Answered** (agent default, 2026-11-20): no. `attempts` is the attempt budget's
  counter and three existing statements (S3, S5, S6 of MIO-010) are written against it meaning
  failures. Re-pointing it would send those back to the spec phase to say the same thing
  differently. A second column that means one thing is cheaper than one column that means two.
