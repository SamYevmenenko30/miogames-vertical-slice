# SPEC: MIO-016 — database timeouts: nothing runs unbounded, and migrations are the exception on purpose

Card: board/3-in-progress/MIO-016-database-timeouts.md · Revision 1 · Author: agent (Claude), 2026-11-21

## Context

The correctness of the money paths here rests on the database: `CHECK (coins >= 0)`,
`UNIQUE (tenant_id, idempotency_key)`, append-only triggers, and `SELECT … FOR UPDATE` over the
balance row. Every one of those mechanisms assumes the statement holding the lock *ends*. Nothing
in this repository made that true: the pools were opened with `max`, `onnotice` and `transform`,
so a statement could run until the connection died, a lock waiter could wait forever, and a
transaction left open between two statements held its rows indefinitely (round two, should-fix
S11).

The failure this prevents is not exotic. A request that opens a transaction, takes
`FOR UPDATE` on a player's balance and then stalls — a slow disk, a paused process, a debugger —
blocks every later debit for that player with no upper bound, and the only remedy is a human with
`pg_terminate_backend`.

## Decisions taken here

- **The limits live on the connection, not in the application.** They are sent as startup
  parameters when the pool opens, so every statement on every connection carries them whether or
  not the code path remembered to. A limit a code path can forget is not a limit.
- **Migrations are deliberately exempt.** A migration that builds an index on a large table is
  *supposed* to take minutes, and cancelling it halfway is worse than waiting. `applyMigrations`
  opens its own connection and sets no statement timeout; this spec pins that with a test, because
  "exempt on purpose" and "forgotten" look identical in a diff.
- **One set of limits per pool, from configuration.** Both pools — the application role's and the
  owner's, which the cross-tenant sweep uses — get the same values. A per-use-case override is the
  kind of knob that gets set once in an incident and never reviewed.
- **A cancelled statement must not poison the pool.** After a timeout the connection goes back to
  the pool and the next query has to succeed; a timeout that quietly breaks the pool trades one
  outage for a worse one.

## Behaviour spec

- **S1 — the limits are in force on an application connection.** On a connection from the
  application pool, `current_setting('statement_timeout')`, `current_setting('lock_timeout')` and
  `current_setting('idle_in_transaction_session_timeout')` equal the configured values. This is the
  assertion that the limits reached the server rather than an object in memory.
- **S2 — a statement that outruns `statement_timeout` is cancelled.** A query that sleeps past the
  limit fails with SQLSTATE `57014` (`query_canceled`), and the **next** query on the same pool
  succeeds.
- **S3 — a lock wait that outruns `lock_timeout` fails instead of waiting.** With one transaction
  holding `SELECT … FOR UPDATE` on a row, a second transaction asking for the same row fails with
  SQLSTATE `55P03` (`lock_not_available`) rather than blocking, and the holder is unaffected.
- **S4 — a transaction left idle past `idle_in_transaction_session_timeout` is terminated, and its
  writes are lost.** After the limit passes, the next statement in that transaction fails
  (`25P03`, or the connection reporting itself terminated), and the row the transaction had
  written is absent afterwards.
- **S5 — migrations are not cut off.** `applyMigrations` applies a migration whose single statement
  runs longer than the application's `statement_timeout` default would allow, and reports it
  applied. (Green at the merge-base: this is a regression guard on a decision, not a
  demonstration of new behaviour — the kind of case `red-check` cannot distinguish, which is
  TD-0012.)
- **S6 — the limits are configuration with defaults, validated.** `loadConfig` reads
  `DB_STATEMENT_TIMEOUT_MS`, `DB_LOCK_TIMEOUT_MS`, `DB_IDLE_IN_TRANSACTION_TIMEOUT_MS` and
  `DB_CONNECT_TIMEOUT_SECONDS`, defaults them, and refuses a value that is not a positive integer
  — naming the variable, as every other configuration error here does.

## Open questions

- **Q1 — what should the numbers be?** → **Answered** (agent default, 2026-11-21): statement
  15 000 ms, lock 5 000 ms, idle-in-transaction 30 000 ms, connect 10 s. The reasoning, since the
  numbers are the whole risk: the slowest thing the application does in one statement is the
  issuance sweep's claim, measured in milliseconds, so 15 s is three orders of magnitude of
  headroom and still ends an outage inside one alert interval; the longest *legitimate* lock wait
  measured in this repository is 558 ms (round one's probe of the ledger's `FOR UPDATE`), so 5 s
  refuses a pathological waiter without touching a contended one; and the HTTP call to an operator
  is outside every transaction by invariant, which is what makes 30 s for an idle transaction
  generous rather than tight. All four are environment variables precisely because a number
  defended in a spec still has to be changeable at 3am.
- **Q2 — should the pool's acquire queue have a timeout too?** → **Answered** (agent default,
  2026-11-21): not in this card. `postgres.js`'s acquire queue is unbounded and untimed, and it
  has no option for this; the alternative is racing every query against a timer in our own code,
  which is a change to every call site and a new way to leak connections. With `statement_timeout`
  in force the queue now drains at a bounded rate, which is the larger half of the problem.
  TD-0013 is rewritten to name the remainder rather than being deleted.
- **Q3 — the same limits on the owner pool, which the cross-tenant sweep uses?** → **Answered**
  (agent default, 2026-11-21): yes. The sweep is a bounded `UPDATE … RETURNING` over claims whose
  lease has expired; if it ever cannot finish inside the statement limit, the limit is not what is
  wrong.

## Out of scope

- Per-query overrides, a circuit breaker (TD-0003), rate limiting (TD-0005).
- `idle_timeout` and `max_lifetime` on the pool: connection recycling is a different concern from
  bounding work, and nothing here has shown a need.
