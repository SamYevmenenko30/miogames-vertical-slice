# SPEC: MIO-006 — gamification: versioned wheel configuration and its admin adapter

Card: board/1-in-spec/MIO-006-wheel-configuration.md · Revision 1 · Author: agent (Claude), 2026-11-20

## Context

An entitlement must draw from the odds it was granted under, which is only possible if
configuration is versioned and never updated in place. This card also establishes that **admin is
an inbound adapter**, not a module: the endpoint that writes wheel versions lives inside the
module that owns them.

## Decisions taken here

- **A new configuration is a new version row.** Nothing updates a live one. The live version is
  the highest for that wheel.
- **Weights are integers and relative.** They do not have to sum to anything; the draw divides by
  their total. A probability table that must sum to 1.0 invites a float.
- **Admin authenticates with the operator's API credentials** as
  `Authorization: Bearer <keyId>.<secret>` over TLS. There are no roles yet (TD-0006), and an
  operator can only ever reach its own tenant.
- **Prize kinds are a closed set**: `coins`, `free_spins`, `bonus_cash`, `nothing`. An unknown
  kind is refused at configuration time, not discovered at spin time.

## Behaviour spec

- **S1 — creating a wheel creates version 1.** `PUT /v1/admin/wheels/welcome` with valid slices
  answers `201` with `version: 1`, and `GET` returns those slices.
- **S2 — a change creates a new version and leaves the old one readable.** A second `PUT` answers
  `version: 2`; the version-1 row still exists with its original slices.
- **S3 — the live version is the highest.** `GET /v1/admin/wheels/welcome` returns version 2
  after the second write, and `?version=1` returns the first.
- **S4 — invalid configuration is refused with a reason.** Each of: fewer than two slices, a
  weight of zero or below, a non-integer weight, a duplicate slice id, an unknown prize kind, and
  a `coins` prize with a non-positive amount, answers `422` naming the problem. No version row is
  created by a refused write.
- **S5 — every admin write is audited.** A successful `PUT` writes one `infra.audit_log` row with
  action `wheel.version.created`, the actor (`admin:<keyId>`), the wheel id and the new version.
- **S6 — the draw is a pure function of the weights and a uniform value.** `weightedPick` returns
  the slice whose cumulative weight interval contains `u * totalWeight`: `0` picks the first
  slice, a value just under 1 picks the last, and over 100,000 uniform draws each slice's share
  is within 1.5 percentage points of its weight share.
- **S7 — tenant isolation.** Tenant B cannot read or write tenant A's wheel: a `GET` for A's
  wheel id under B's credentials answers `404`, and a `PUT` under B creates B's own wheel with
  version 1 rather than touching A's.

## Open questions

- **S/Q1 — may a wheel version be deleted or rolled back?** → **Answered** (agent default,
  2026-11-20): no deletion. A rollback is a new version with the old slices, which keeps the
  history honest and means an entitlement pinned to the bad version still draws from what it was
  promised.
- **Q2 — who may change odds?** → **Answered** (agent default, 2026-11-20): any holder of the
  tenant's API credentials, which is too coarse and is recorded as TD-0006. The audit log names
  the key id used, so a change is always attributable to a credential.

## Out of scope

- Granting entitlements (MIO-005), the draw at spin time (MIO-007), roles (TD-0006).
