# SPEC: MIO-002 — identity: tenants, API credentials, players and the external-id mapping

Card: board/1-in-spec/MIO-002-identity-tenants-players.md · Revision 1 · Author: agent (Claude), 2026-11-20

## Context

Nothing can be scoped to a tenant until a tenant exists, and no event can name a player until the
mapping between the operator's player id and ours does. This module answers two questions and no
others: *who is calling* and *whose player is this*.

Governed by [ADR-0006](../decisions/ADR-0006-tenant-isolation-in-depth.md). The module owns
`identity.*` tables and depends on no other module.

## Decisions taken here

- **A tenant is a casino operator.** One operator, one tenant, one set of credentials.
- **The key id travels in the clear, the secret never does.** We store a SHA-256 hash of the
  secret; authentication re-derives it. A leaked database does not yield signing secrets.
- **Players are provisioned from authenticated operator events only.** There is no code path from
  a client-supplied identifier to a new player row.
- **The player API is reached with a short-lived token the operator exchanges for**, server to
  server, using its API credentials. The alternative — trusting an operator-issued JWT — means
  accepting ten different signing schemes and trusting ten key rotations.

## Behaviour spec

- **S1 — an active key id resolves to its tenant.** `authenticate(keyId, secret)` returns the
  tenant and the key's operator for a key whose secret matches.
- **S2 — a wrong secret does not authenticate, and says nothing more.** The result is the same
  "not authenticated" for a wrong secret, an unknown key id and a deactivated key: the caller
  cannot distinguish them.
- **S3 — the secret is never stored in the clear.** No column of `identity.tenant_api_key`
  contains the secret; the stored digest differs from the secret and verification still succeeds.
- **S4 — a deactivated key stops authenticating immediately.** Deactivating a key makes the next
  authentication fail without touching the tenant.
- **S5 — a player is provisioned on first sight.** `ensurePlayer(externalPlayerId)` under tenant A
  creates one player and one identity row, and returns an internal id.
- **S6 — provisioning is idempotent.** Calling it twice with the same external id returns the same
  internal player id and leaves exactly one identity row. Two concurrent first-sights also yield
  one player (the unique constraint decides, not a prior read).
- **S7 — the same external id in two tenants is two different players.** Tenant A's `player-77`
  and tenant B's `player-77` have different internal ids and neither can see the other.
- **S8 — lookup never creates.** `findPlayerByExternalId` returns null for an unknown external id
  and creates nothing.
- **S9 — a player token carries the tenant and the player, signed.** `issuePlayerToken` produces a
  token that `verifyPlayerToken` resolves back to the same tenant and player.
- **S10 — a tampered or foreign token does not verify.** Changing any character of the token, or
  re-signing its body with a different secret, fails verification; so does a token whose payload
  names another tenant than the signature covers.
- **S11 — an expired token does not verify.** A token issued with a one-second lifetime fails once
  the clock has moved past its expiry, and the failure names expiry rather than tampering.
- **S12 — tenant isolation.** Acting as tenant B, no query of this module returns tenant A's
  player, identity or key: `findPlayerById(tenantA.playerId)` is null, and `authenticate` with
  tenant A's key id under tenant B's scope resolves to tenant A's own tenant id rather than
  leaking into B's.

## Open questions

- **Q1 — can one operator have several brands under one tenant?** Real casino groups run several
  skins over one platform. → **Answered** (agent default, 2026-11-20): not in this slice. A brand
  would be a column on the tenant's rows and a second partition key everywhere, which doubles the
  isolation surface for no gain here. Recorded in `docs/scaling.md` as a known future partition.
- **Q2 — does a player token survive a key rotation?** → **Answered** (agent default,
  2026-11-20): yes. Player tokens are signed with the platform secret, not the tenant's API
  secret, so rotating an operator's credentials does not log its players out. The tenant id is
  inside the signed payload, so a rotated key cannot be used to mint tokens for another tenant.

## Out of scope

- Key rotation endpoints and roles (TD-0006).
