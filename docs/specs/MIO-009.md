# SPEC: MIO-009 — rewards: the bonus store and an idempotent redemption

Card: board/1-in-spec/MIO-009-bonus-store-redemption.md · Revision 1 · Author: agent (Claude), 2026-11-20

## Context

Step 6 of Part B and the duplicate-redemption case of Part C. The debit and the intent must be one
transaction; the external call must not be inside it.

## Decisions taken here

- **`Idempotency-Key` is required**, not optional. A redemption without one is a request we
  cannot make safe, so it is refused rather than accepted hopefully.
- **The key is scoped to the tenant and the player.** The same key from a different player is a
  different redemption — one player's retry must not return another's receipt.
- **Coins leave the balance when the redemption is created**, not when the operator confirms. The
  alternative — reserve, then debit — is a second state to reconcile for no gain, because a
  failed issuance refunds (Sam, 2026-11-20).

## Behaviour spec

- **S1 — a store item is configured per tenant.** `PUT /v1/admin/store-items/:itemId` with a
  price in coins and a reward payload answers `201`; `GET /v1/store-items` (player token) lists
  the tenant's items with their prices.
- **S2 — a redemption debits the coins and records the intent, in one transaction.**
  `POST /v1/redemptions` with `Idempotency-Key` and a known item answers `202` with a
  `redemptionId` and `status: "pending_issuance"`; the balance drops by the price; one
  `rewards.redemption.requested` outbox row exists.
- **S3 — a replay returns the first redemption and debits once.** The same `Idempotency-Key`
  answers `200` with the same `redemptionId`, the balance is unchanged by the second call, and
  there is still exactly one outbox row and one ledger debit.
- **S4 — the same key from another player is a different redemption.**
- **S5 — an insufficient balance is `422` and changes nothing.** No redemption row, no debit, no
  outbox row, and the problem body carries the balance and the price.
- **S6 — an unknown or another tenant's item is `404`.**
- **S7 — a missing `Idempotency-Key` is `400`** with a machine-readable type.
- **S8 — the status is readable.** `GET /v1/redemptions/:id` returns the redemption's status,
  item, price and creation time; another player's redemption id is `404`.
- **S9 — concurrent duplicates produce one redemption.** Five simultaneous requests with the same
  key yield one `redemptionId`, one debit, one outbox row.
- **S10 — tenant isolation.** A redemption id from tenant A is `404` under tenant B, and the same
  `Idempotency-Key` in two tenants is two redemptions.

## Open questions

- **Q1 — may a player redeem the same item twice?** → **Answered** (agent default, 2026-11-20):
  yes, with a different idempotency key. The store sells repeatables; a per-item limit is a
  product feature, not an invariant, and would belong on the item row.
- **Q2 — what happens to a `pending_issuance` redemption if the item is later removed?** →
  **Answered** (agent default, 2026-11-20): the redemption carries its own price and reward
  payload, copied at creation. Deleting an item does not change a redemption in flight — the same
  reason a spin pins its wheel version.
