# SPEC: MIO-005 — gamification: reward rules turn a deposit into spin entitlements

Card: board/1-in-spec/MIO-005-rules-to-entitlements.md · Revision 1 · Author: agent (Claude), 2026-11-20

## Context

Step 3 of Part B: the canonical deposit event becomes spin entitlements. Rules are data so that a
new rule is a row; evaluation is a pure function so that it is testable without a database.

## Decisions taken here

- **Tiered rules, decided by Sam (2026-11-20):** a rule is "deposit ≥ X in currency C → N spins
  of wheel W". The highest matching threshold wins and **only one rule applies**. Proportional
  granting ("one spin per €25") was the alternative and was rejected: it needs a per-event cap
  and makes the cost of a promotion unpredictable.
- **An unused entitlement lives 7 days**, decided by Sam (2026-11-20), configurable per rule.
- **The wheel version is pinned at grant time**, and the server seed is generated and committed
  (its hash stored) then too — so the odds and the outcome are both fixed before the player acts.
- **This consumer provisions the player.** Ingestion deliberately does not (MIO-004 S7): a player
  row should appear when something is granted to it, not when a payload is parsed.

## Behaviour spec

- **S1 — a deposit at or above a rule's threshold grants that rule's spins.** With a rule
  "≥ 20 EUR → 2 spins of `welcome`", a 50 EUR deposit creates two `granted` entitlements for the
  player, both pinned to `welcome` and to the wheel's live version.
- **S2 — each entitlement carries a committed seed.** Every entitlement has a distinct 64-hex
  `serverSeed` and a `seedHash` equal to SHA-256 of it. No two entitlements share a seed.
- **S3 — a deposit below every threshold grants nothing**, and the event is still recorded as
  processed, so it is not retried forever.
- **S4 — the highest matching tier wins, and only one rule applies.** With rules
  "≥ 20 → 1 spin" and "≥ 100 → 5 spins", a 150 EUR deposit grants exactly 5 — not 6.
- **S5 — the consumer is idempotent.** Delivering the same event twice grants the spins once.
- **S6 — the player is provisioned here.** Before the event, no `identity.player` row exists for
  the external id; after it, exactly one does, and a second deposit from the same external id
  reuses it.
- **S7 — an entitlement expires after the rule's TTL.** `expiresAt` is `grantedAt` plus the
  rule's `ttlHours` (7 days by default), computed from the injected clock.
- **S8 — a rule only matches its own currency.** A rule in EUR does not match a USD deposit of
  the same numeric amount.
- **S9 — tenant isolation.** A tenant with no rules grants nothing for an identical deposit, and
  entitlements are never visible across tenants.

## Open questions

- **Q1 — what if the rule names a wheel that has no version?** → **Answered** (agent default,
  2026-11-20): the grant fails and the event is retried, rather than granting an entitlement with
  no odds. A rule pointing at an unconfigured wheel is an admin error that should be loud; the
  outbox retry and the `last_error` column make it visible.
- **Q2 — should a deposit that matches no rule be recorded anywhere?** → **Answered** (agent
  default, 2026-11-20): the processed-event row is enough. The envelope already records the
  deposit, and a "nothing happened" table would be a log pretending to be data.

## Out of scope

- Spending an entitlement (MIO-007), expiry sweeping (TD-0004), admin endpoints for rules
  (the seed script creates them; an endpoint is the same adapter pattern as MIO-006).
