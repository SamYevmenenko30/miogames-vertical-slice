# SPEC: MIO-011 — tenant isolation in three layers, with a test per layer

Card: board/1-in-spec/MIO-011-tenant-isolation-in-depth.md · Revision 1 · Author: agent (Claude), 2026-11-20

## Context

A cross-tenant leak is the one bug that ends a B2B platform, and the realistic failure mode is a
`WHERE` clause someone forgot — not an exploit. Two of the three layers in
[ADR-0006](../decisions/ADR-0006-tenant-isolation-in-depth.md) are already built and tested: the
tenant lives in context with no un-scoped accessor, and another tenant's resource answers `404`.
This card adds the third, which is the one that survives a mistake in the first two.

## Decisions taken here

- **The application connects as a NON-OWNER role.** Row-level security does not apply to a table's
  owner, so policies written against an owner connection are decoration. `DATABASE_URL` is the
  application role; migrations and the one deliberate cross-tenant job use the owner, through
  `DATABASE_OWNER_URL`.
- **The tenant reaches the database as a transaction-local setting**, `SET LOCAL app.tenant_id`,
  issued by the unit of work. `SET LOCAL` and not `SET`: a pooled connection must not carry one
  request's tenant into the next.
- **With no tenant set, tenant-owned tables return nothing.** The policy compares against
  `current_setting('app.tenant_id', true)`, which is NULL when unset, so the predicate is false.
  Failing closed is the only safe default for a policy.
- **The retry sweep is the single legitimate cross-tenant read**, and it runs on the owner
  connection, reads only ids and tenant ids, and then enters each tenant properly. It is named
  here so that a second such path has to argue for itself.
- **The append-only tables lose `DELETE` and `TRUNCATE` from the application role** — which is
  what TD-0010 said the real control was.

## Behaviour spec

- **S1 — the application role cannot see another tenant's rows, even without a `WHERE`.** As the
  application role with `app.tenant_id = 'tenant-a'`, `SELECT * FROM ledger.balance` returns only
  tenant A's rows, although the statement names no tenant.
- **S2 — with no tenant set, a tenant-owned table returns nothing.** The same bare `SELECT`
  outside a tenant scope returns zero rows rather than everything.
- **S3 — an `INSERT` for another tenant is refused.** As `tenant-a`, inserting a row whose
  `tenant_id` is `tenant-b` violates the policy.
- **S4 — an `UPDATE` cannot reach another tenant's row.** As `tenant-a`, updating tenant B's
  balance by primary key affects zero rows.
- **S5 — the setting is transaction-local.** After a transaction that set `tenant-a`, a new
  transaction on the same pooled connection starts with no tenant and therefore sees nothing.
- **S6 — the application role cannot delete or truncate an append-only table.** `DELETE FROM
  ledger.entry` and `TRUNCATE infra.audit_log` are both refused for lack of privilege, not by a
  trigger.
- **S7 — every tenant-owned table carries a policy.** A test enumerates the tenant-owned tables
  from the schema and asserts each one has row-level security enabled and at least one policy;
  a new table without one fails.
- **S8 — the whole suite still passes through the application role.** Every existing integration
  test runs against a database where RLS is on, which is what makes S1–S6 more than a laboratory
  result.

## Open questions

- **Q1 — should the worker run entirely as the owner?** → **Answered** (agent default,
  2026-11-20): no. Only the sweep that looks for due work across tenants uses the owner
  connection; everything the worker does afterwards runs in a tenant scope on the application
  role, so a consumer bug cannot read across tenants either.
- **Q2 — what about `infra.outbox`?** → **Answered** (agent default, 2026-11-20): it carries a
  tenant id but it is platform plumbing read by the relay across tenants by design, so it gets no
  policy. The relay hands each event's tenant to the consumer, which then runs scoped. Named here
  so the exception is visible rather than discovered.

## Out of scope

- A database per tenant (rejected in ADR-0006), roles for admin users (TD-0006).
