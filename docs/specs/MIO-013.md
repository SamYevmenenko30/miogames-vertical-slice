# SPEC: MIO-013 — an end-to-end smoke run, and the sample requests it captures

Card: board/1-in-spec/MIO-013-smoke-run-and-samples.md · Revision 1 · Author: agent (Claude), 2026-11-20

## Context

A reviewer should be able to see all eight Part B steps happen on their own machine, for both
operators, in under a minute — and the sample request/response pairs the assignment asks for
should be *captured from that run* rather than written by hand, because a hand-written sample is a
claim and a captured one is evidence.

MIO-011 made the case for this card sharper than it was: `pnpm dev` had never worked, because
nothing automated ran it. A path nothing exercises is a path that does not work.

## Decisions taken here

- **The smoke run asserts.** It is not a demo that prints things; every step checks what it got
  and the run exits non-zero on the first failure. That is what lets CI run it.
- **It drives real HTTP against the real composition**, with the simulated operators in their own
  process-local server, and it drains the outbox the way the worker does rather than mocking the
  worker away.
- **It writes `docs/samples/*.http` from what it actually sent and received**, including the
  duplicate-delivery answers.
- **This card's proof is the script's own exit code**, run by CI on every push. It adds no
  `*.spec.ts`, because a vitest wrapper around a script that already asserts would only move the
  assertions somewhere less readable.

## Behaviour spec

- **S1 — the full flow succeeds for operator A.** Deposit event accepted → entitlements granted →
  session minted → spin drawn with coins credited → store listed → redemption accepted → reward
  issued → status `issued` with the operator's reference. Every step asserted, the run exits 0.
- **S2 — the full flow succeeds for operator B**, whose event schema and reward API differ at both
  ends, with no change in the steps between them.
- **S3 — the replays cause no second effect.** Re-posting the same deposit answers `200`
  `duplicate` with the original event id and grants no further entitlement; re-posting the
  redemption with the same `Idempotency-Key` answers `200` with the same redemption id and debits
  nothing further.
- **S4 — the spin is recomputed from what the response revealed.** The run takes the revealed
  seed and the spin id, recomputes `weightedPick(slices, uniform01(seed, spinId))` itself, and
  asserts the slice matches — and that `sha256(seed)` equals the committed hash.
- **S5 — the balance arithmetic is checked, not narrated.** Coins credited by the spin minus the
  item price equals the balance the API reports afterwards.
- **S6 — the samples are written from the run.** `docs/samples/` contains the request and response
  for each step of both operators, including the duplicate answers, with secrets redacted.

## Open questions

- **Q1 — should the smoke run against `docker compose up` instead of starting its own API?** →
  **Answered** (agent default, 2026-11-20): it starts its own, so `pnpm smoke` needs only Postgres
  and works in CI without a compose-aware runner. The compose stack exists for a reviewer who
  wants to poke the API by hand, and the Dockerfile is built by CI separately.
- **Q2 — does it reset the database?** → **Answered** (agent default, 2026-11-20): it creates its
  own database, migrates it and drops it at the end, exactly as the integration tests do. A smoke
  run that mutates the development database would be a smoke run people stop running.

## Out of scope

- A browser or UI, load testing, running against a deployed environment.

## Tests this spec expects

The script is the test: `pnpm smoke` asserts every statement above and exits non-zero on the
first failure. CI runs it on every push.
