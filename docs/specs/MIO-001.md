# SPEC: MIO-001 — Platform: config, unit-of-work, tenant-scoped queries, outbox, problem+json

Card: board/1-in-spec/MIO-001-platform-foundation.md · Revision 1 · Author: agent (Claude), 2026-11-20

## Context

Six modules will share one transaction model, one error shape, one way to emit an event and one
way to scope a query to a tenant. Building any of those twice is how the invariants diverge, so
they are built once, here, before the first business rule exists.

Governed by [ADR-0001](../decisions/ADR-0001-modular-monolith-first.md) (one transaction per
use-case), [ADR-0003](../decisions/ADR-0003-idempotency-outbox-and-retries.md) (outbox, idempotent
consumers) and [ADR-0006](../decisions/ADR-0006-tenant-isolation-in-depth.md) (scoped queries).
Row-level security is explicitly **not** here — it arrives with its tests in MIO-011.

## Decisions taken here

- **Postgres is the queue.** The outbox is a table, the relay is a poll loop with
  `FOR UPDATE SKIP LOCKED`. No broker (ADR-0003).
- **Migrations are files, applied explicitly.** Never at application boot: two replicas starting
  together race through the same migration.
- **The unit-of-work is re-entrant.** A nested `withTransaction` joins the outer one rather than
  opening a second — otherwise "one transaction per use-case" becomes a lie the moment a facade
  calls a facade.
- **There is no un-scoped repository accessor.** Tenant scoping is not a convention a developer
  remembers; it is the only API available.

## Behaviour spec

- **S1 — a missing required setting fails at startup, by name.** Loading the configuration
  without `DATABASE_URL` throws an error whose message names `DATABASE_URL`. It does not fall
  back to a default and does not start.
- **S2 — a malformed setting fails at startup, by name and reason.** `OUTBOX_POLL_MS=abc`
  throws naming `OUTBOX_POLL_MS`; `DATABASE_URL=not-a-url` throws naming `DATABASE_URL`.
- **S3 — configuration is read in exactly one place.** The loaded object is frozen, and the only
  module reading `process.env` is `platform/config` (enforced by lint, probed by `gate-probes`).
- **S4 — a nested transaction joins the outer one.** `withTransaction(() => withTransaction(fn))`
  executes `fn` on the same connection and the same transaction; a rollback of the outer
  transaction undoes work the inner one did.
- **S5 — a throw inside a transaction rolls everything back.** A use-case that inserts two rows
  and then throws leaves no row behind.
- **S6 — a query outside a transaction is refused.** Obtaining the transactional client when no
  unit-of-work is open throws, rather than silently running on an auto-commit connection.
- **S7 — the tenant must be in context.** `currentTenantId()` throws outside a tenant scope, and
  `withTenant(id, fn)` makes it available to everything `fn` calls, including through an `await`.
- **S8 — a scoped query carries the tenant predicate.** A `scoped(table)` select for tenant A
  returns only tenant A's rows when both tenants have rows with the same natural key.
- **S9 — an event published in a rolled-back transaction is never relayed.** Publishing inside a
  transaction that then throws leaves no outbox row.
- **S10 — the relay dispatches each event at least once and claims it exclusively.** Two relay
  instances polling the same outbox never dispatch the same row concurrently
  (`FOR UPDATE SKIP LOCKED`), and a row survives a dispatcher crash (it is only marked published
  after the handler's transaction commits).
- **S11 — a consumer runs its effect once per event.** Delivering the same event twice to an
  idempotent consumer performs the effect once; the second delivery is a no-op that still
  acknowledges.
- **S12 — a consumer's effect and its processed-event record commit together.** If the handler
  throws, neither the effect nor the record is persisted, and the event is retried.
- **S13 — errors are RFC 9457 problem+json.** A known application error renders
  `application/problem+json` with `type`, `title`, `status`, `detail` and `instance`, and the
  status matches the error class (404 not-found, 409 conflict, 422 unprocessable, 401
  unauthorized).
- **S14 — an unexpected error leaks nothing.** An unhandled exception renders status 500 with a
  generic title, no stack trace, no SQL and no internal identifier, while logging the detail
  server-side with the request's trace id.
- **S15 — HMAC verification is constant-time and rejects tampering.** A signature computed over a
  different body, a different secret or a timestamp outside the tolerance window is rejected;
  verification uses a timing-safe comparison.
- **S16 — the draw primitive is deterministic and uniform.** `uniform01(seed, label)` returns the
  same value for the same inputs, a different one for a different label, and over 100,000 samples
  its mean lies within 0.01 of 0.5.
- **S17 — the audit log is append-only.** An `UPDATE` or `DELETE` on `infra.audit_log` is refused
  by the database, not by the application.
- **S18 — migrations apply in order, once.** The runner applies pending files in filename order,
  records each, and a second run applies nothing. A file that fails leaves its own transaction
  rolled back and the runner exits non-zero without recording it.
- **S19 — time is injected.** `Clock` is a provider; a test can fix it, and advancing a fixed
  clock changes what the application believes "now" is.

## Open questions

- **Q1 — does the relay guarantee ordering per aggregate?** At-least-once delivery with
  `SKIP LOCKED` means two events for the same player can be processed out of order, which matters
  if a later ticket adds an event whose effect depends on an earlier one. → **Answered** (agent
  default, 2026-11-20): no ordering guarantee, and no consumer in this slice may depend on one —
  each consumer's effect is idempotent and commutative (grant entitlements, credit coins). If a
  future feature needs ordering, the relay claims by `(aggregate_type, aggregate_id)` rather than
  by row, which is a change to one query. Recorded as a constraint in the module AGENTS.md so a
  later ticket cannot quietly assume otherwise.
- **Q2 — how long does a failed outbox row keep being retried?** → **Answered** (agent default,
  2026-11-20): forever, with exponential backoff capped at five minutes, and an `attempts`
  counter that an operator can see. Dropping a domain event silently is worse than a queue that
  visibly grows; a dead-letter decision belongs to the ticket that first needs one.

## Out of scope

- Row-level security and the non-owner application role (MIO-011).
- Metrics and tracing backends (MIO-012 names what we would emit).
- Any business table. This ticket owns only `infra.*`.
